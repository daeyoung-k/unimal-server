# 지도 바텀카드 피드 API 설계

작성일: 2026-07-29
개정: 2026-07-29 (반경/행정동 필터 폐기 → 거리 정렬 단일 섹션)
관련 구현 계획: `docs/plans/2026-07-29-지도-바텀카드-피드-구현.md`

## 1. 배경

지도 화면은 지금 마커만 있다. 사용자가 지도에 진입해도 "여기 뭐가 있는지" 알려면
마커를 하나하나 눌러야 한다. 마커는 탐색 도구지 소비 도구가 아니다.

당근마켓 동네지도는 이 문제를 **바텀시트 카드 피드**로 푼다. 지도는 위치 맥락만
제공하고, 실제 콘텐츠 소비는 하단 카드 리스트에서 일어난다. 사용자는 아무것도
누르지 않아도 스크롤만으로 뭐가 올라왔는지 파악한다.

스토맵에 같은 구조를 넣는다. 목표는 **지도 진입 직후 1 RTT 안에 "지금 볼 만한 것"을
내려주는 API**.

### 이 문서를 개정한 이유 — 밀도가 설계를 지배한다

초안은 당근마켓을 그대로 따라 **반경 기반 `LATEST`/`HOT` + 행정동 기반 `NEARBY`**
3섹션으로 설계했다. 이건 **글이 충분히 많다는 전제**에서만 성립한다.

스토맵의 현실은 다르다. 출시는 했지만 홍보를 하지 않아서 **실사용자가 사실상 없고,
글도 거의 없다.** 이 상태에서 반경 기반 피드를 붙이면:

- 줌 14(5km) 기준으로 반경 안에 글이 0~2건. 초안의 "3건 미만 섹션 숨김" 정책까지
  걸리면 결과는 `sections: []` → **피드 첫 화면이 백지.**
- 백지 피드는 기능을 안 넣은 것보다 나쁘다. 화면 하단을 차지하면서 아무 정보도 주지 않는다.

게다가 `ZoomLevel.ZOOM_6` 은 이미 반경 800km(한반도 전체)다. 줌아웃하면 초안 설계도
사실상 "전국 전체 조회"였다. **반경은 이미 실질적인 필터가 아니었다.**

그래서 방향을 바꾼다.

> **반경·행정동을 필터에서 빼고, 거리를 정렬 기준으로만 쓴다.**
> 섹션은 지금 1개로 시작하고, 응답 구조는 여러 섹션을 담을 수 있게 유지한다.

## 2. 무엇을 보여주나 — 섹션 1종으로 시작

| 타입 | 헤더 문구 | 기준 |
| --- | --- | --- |
| `NEAR` | 지금 여기 이야기 | 반경 제한 없음. 현재 위치에서 **가까운 순**(KNN), 20건 |

### 왜 섹션을 3개에서 1개로 줄이나

초안의 3섹션은 **모집단이 서로 달랐기 때문에** 값이 있었다.
`LATEST`/`HOT` 은 반경 안, `NEARBY` 는 행정동 전체 — 서로 다른 글이 나온다.

반경을 없애서 모집단을 전국으로 통합하면 **세 섹션이 같은 풀을 나눠 갖는다.**
게다가 초안의 중복 제거 규칙(`LATEST` > `HOT` > `NEARBY`)까지 걸려 있어서:

- 전체 글이 30건이면 10 + 10 + 10 으로 풀이 정확히 소진된다. 세 섹션 다
  "남은 것 긁어모은" 상태가 된다.
- `HOT` 은 반응 0인 글을 제외하므로 3건을 못 채워 숨겨질 확률이 높고, 그러면 남는 건
  `NEAR`/`LATEST` 두 개인데 **같은 글이 순서만 다르게** 놓인다.

섹션을 나누는 건 "각 섹션이 서로 다른 발견 경험을 준다"는 전제가 있을 때만 값을 한다.
풀이 작으면 섹션 나누기는 빈약함을 3배로 늘리는 일이다.

### 언제 섹션을 늘리나

기준: **섹션당 노출 20건 × 섹션 수 × 2배** 정도의 공개 글이 쌓였을 때.
3섹션이면 대략 **공개 글 1,200건** 이상. 그때 `LATEST`(최신순), `HOT`(시간감쇠 인기순)을
추가한다. 아래 §4의 `sections` 배열 구조 덕에 **서버 상수만 바꾸면 되고 앱 재배포는 불필요하다.**

`HOT` 점수식은 나중에 쓸 것이므로 근거만 남겨둔다 (Hacker News 계열 시간감쇠).

```
hot = (likes × 2 + replies × 3) / (경과시간h + 2)^1.5
```

- 분자: 댓글(3)을 좋아요(2)보다 높게 본다. 댓글은 비용이 큰 참여다.
- 분모 `+2`: 방금 올라온 글의 점수가 발산하는 걸 막는다.
- 지수 `1.5`: 하루 지나면 약 1/9 로 떨어져 어제 인기 글이 상단을 영구 점유하지 못한다.

### 거리를 필터가 아니라 정렬로 쓰는 이유

`ORDER BY location <-> point` (PostGIS KNN)는 반경 파라미터가 없다.

- **밀도가 낮으면** 자동으로 먼 글까지 채운다 → 피드가 절대 비지 않는다.
- **밀도가 높아지면** 자동으로 가까운 글만 상단에 온다 → 별도 조치 없이 "동네 피드"가 된다.
- **튜닝 파라미터가 사라진다.** 반경을 몇 m 로 할지 고민할 필요가 없다.

되돌리기도 이쪽이 싸다. 나중에 반경 캡을 씌우려면 `WHERE ST_DWithin(...)` 한 줄을
추가하면 끝이다. 반대로 반경 기반으로 짜놓고 나중에 푸는 건 API 파라미터·인덱스·앱까지
전부 얽혀서 비싸다.

### 거리를 응답에 내려준다

전국이 대상이므로 카드가 324km 떨어진 글일 수 있다. 이걸 숨기면 탭했을 때 지도가
갑자기 부산으로 튀어서 사용자가 혼란스럽다. **`distanceMeters` 를 내려주고 앱이
"3.2km" / "324km" 로 표시한다.** 정직하게 보여주면 튀는 게 혼란이 아니라 탐색이 된다.

### 빈 섹션 정책 — 초안에서 변경

초안은 `MIN_SECTION_SIZE = 3` 이었다. **1로 내린다.** 즉 항목이 1건이라도 있으면 섹션을
내려보낸다. 지금 밀도에서 3건 문턱은 피드를 백지로 만드는 원인이다.

글이 아예 0건이면 `sections: []` 을 내려보내고, 앱은 바텀시트를 접거나 빈 상태 문구를
띄운다 (앱 결정).

## 3. 엔드포인트

```
GET /board/map/feed
```

인증: `@OptionalUserInfoAnnotation` (비로그인도 조회 가능 — 온보딩에서 지도를 먼저
보여주는 흐름을 막지 않는다). 게이트웨이는 `OptionalAccessTokenFilter` 경로.

> 기존 `/board/map/location/post`, `/board/map/post` 는 `@UserInfoAnnotation`(필수)이다.
> 피드는 로그인을 요구할 이유가 없다.

### 요청

| 파라미터 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `latitude` | Double | O | 지도 중심 위도 |
| `longitude` | Double | O | 지도 중심 경도 |
| `zoom` | Int | X | **현재 미사용.** 향후 반경 캡 도입 대비 |

`@ModelAttribute` 바인딩. 별도 DTO(`MapFeedRequest`)로 만든다.

초안에 있던 `siDo` / `guGun` / `dong` 은 **전부 삭제**한다. 행정동 섹션이 없어졌으므로
필요 없다. 이 삭제로 함께 사라지는 것들:

- map 서비스 gRPC 역지오코딩 호출과 실패 폴백 처리
- `geo:dong:v1:{lat3}:{lng3}` 캐시 (Google Geocoding API 과금 회피용)
- 동명이인(`중앙동`, `신흥동` 등) 방지를 위한 `si_do + gu_gun + dong` 3중 매칭 규칙
- native query 의 `CAST(:dong AS text)` NULL 파라미터 타입추론 함정
- `idx_board_area_created` 신규 인덱스

**`zoom` 을 미사용인데도 받는 이유:** 밀도가 오르면 `NEAR` 에 반경 캡을 씌우게 되는데,
그때 앱이 이미 `zoom` 을 보내고 있으면 **서버만 배포하면 된다.** 앱 v1 부터 보내게 해둔다.
아래 `hasMore` 를 미리 내려두는 것과 같은 이유다. 다만 지금은 쿼리에 영향이 없다는 걸
문서에 명시해서, 나중에 "zoom 바꿨는데 왜 안 변하지" 로 시간을 태우지 않게 한다.

## 4. 응답

```json
{
  "code": 200,
  "message": "Success",
  "data": {
    "sections": [
      {
        "type": "NEAR",
        "title": "지금 여기 이야기",
        "has_more": true,
        "items": [
          {
            "board_id": "aB3xY9",
            "thumbnail_url": "https://cdn.unimal.co.kr/images/thumb/...",
            "image_url": "https://cdn.unimal.co.kr/images/...",
            "title": "역삼동 골목 고양이",
            "content": "퇴근길에 만난 삼색이",
            "street_name": "서울 강남구 역삼로 123",
            "dong": "역삼동",
            "latitude": 37.5006,
            "longitude": 127.0366,
            "distance_meters": 320,
            "nickname": "대영",
            "profile_image": "https://cdn.unimal.co.kr/...",
            "like_count": 12,
            "reply_count": 3,
            "created_at": "2026-07-29T14:33:00"
          }
        ]
      }
    ]
  }
}
```

`CommonResponse(data = MapFeedResponse)` 로 감싼다 (기존 관례 유지).

초안의 `dong` 최상위 필드는 삭제한다 (역지오코딩을 안 하므로 서버가 모른다).
카드별 `dong` 은 `board.dong` 컬럼에 이미 저장돼 있으므로 그대로 내려준다.

### `sections` 를 배열로 두는 것이 이 설계의 핵심 자산이다

섹션이 1개인데 배열로 감싸는 건 지금은 과해 보인다. **의도적이다.**

- 밀도가 오르면 `LATEST`/`HOT` 을 **서버에서만** 추가할 수 있다.
- 나중에 `type: "AD"`, `type: "NOTICE"` 를 순서 조정만으로 끼워넣을 수 있다.

**단, 앱이 "모르는 `type` 은 무시" 로직을 v1 부터 넣어야 한다.** 안 넣으면 나중에 섹션을
추가할 때 구버전 앱이 깨진다. 이건 서버가 강제할 수 없으므로 앱 쪽 필수 요구사항이다.

### 썸네일 — `thumbUrl` 우선, `fileUrl` 폴백

`1fe7a37`(2026-07-29) 에서 `board_file.thumb_key` / `thumb_url` 이 추가됐다.
마커용 400px JPEG 파생이다. **초안은 이 커밋 전에 작성돼서 `file_url` 만 썼다 — 정정한다.**

- `thumbnailUrl` = `COALESCE(bf.thumb_url, bf.file_url)`
  기존 파일은 백필이 없어 `thumb_url` 이 null 이므로 원본으로 폴백한다.
- `imageUrl` = `bf.file_url` (원본)

**둘 다 내려준다.** 400px 파생은 컴팩트 행 썸네일(80dp)에는 충분하지만 풀폭 카드에는
흐릿하다. 카드 크기는 앱 디자인 결정이므로 서버가 선점하지 않는다. 같은 LATERAL 행에서
두 컬럼을 함께 읽으므로 **추가 쿼리 비용이 0이다.**

### 사진 없는 글도 포함한다 — 초안에서 변경

초안은 `INNER JOIN LATERAL board_file` 로 **사진 없는 글을 제외**했다.
지금 밀도에서는 이 필터가 피드를 비울 수 있어서 `LEFT JOIN LATERAL` 로 바꾼다.
`thumbnailUrl` / `imageUrl` 은 **nullable** 이고 앱이 플레이스홀더를 그린다.

> 참고 — 문서 정정: 루트 `CLAUDE.md` 와 `unimal-server/CLAUDE.md` 는 마커 조회가
> "INNER JOIN LATERAL board_file → 사진 없는 게시물 제외" 라고 적고 있는데,
> **실제 `MapBoardRepositoryImpl` 은 그렇지 않다.** 사진 없는 글도
> `OR b.created_at >= NOW() - INTERVAL '48 hours'` 로 48시간은 노출하고,
> 사진 보유는 `+3.0` score 가산으로만 반영한다. 문서가 의도를 적었고 코드가 다른 길로 갔다.

밀도가 오르면 `LEFT` → `JOIN` 한 단어만 바꾸면 사진 필수가 된다.

### 키 컨벤션: snake_case (2026-07-29 결정)

**내부 Kotlin 프로퍼티는 camelCase, 응답 JSON 키는 snake_case.**
이게 프로젝트 표준이다 (`unimal-server/CLAUDE.md` 네이밍 규칙 참고).

> 이 문서 초안은 "신규 API는 camelCase 로 통일" 이라고 적었으나 **뒤집혔다.**
> 지금 레포는 `MapPostInfo` 가 snake_case, `PostInfo` 가 camelCase 로 갈려 있는데,
> 수렴 방향을 **snake_case 로 정했다.** 앱이 이미 snake_case 를 파싱하고 있고
> (`profile_image`, `created_at`, `file_info_list`), 지도 관련 응답이 그쪽이라
> 피드도 맞추는 게 앱 코드에 일관된다.

구현은 **클래스 레벨 `@JsonNaming` 하나**로 한다.

```kotlin
@JsonNaming(PropertyNamingStrategies.SnakeCaseStrategy::class)
data class MapFeedCard(
    val boardId: String,        // → "board_id"
    val thumbnailUrl: String?,  // → "thumbnail_url"
)
```

`MapPostInfo` 처럼 **필드마다 `@JsonProperty` 를 나열하지 않는다.** 그 방식은 필드를
추가할 때 어노테이션을 빼먹으면 그 키만 조용히 camelCase 로 새고 앱에서 `null` 로 읽힌다.
클래스 레벨 어노테이션이면 그 사고가 구조적으로 불가능하다.

**전역 설정(`spring.jackson.property-naming-strategy`)은 쓰지 않는다** —
`PostInfo` 등 기존 camelCase 응답이 전부 깨져서 앱이 죽는다. 기존 API 수렴은 앱 동시
배포가 가능한 시점에 별도 작업으로 한다 (이 문서 범위 밖).

### `isLike` / `isOwner` / `score` 를 응답에서 뺐다

기존 `MapPostInfo` 에는 `isLike`, `isOwner` 가 있다. 마커에는 필요하다 — 링 색이 달라지니까.
**카드에는 필요 없다.** 카드는 썸네일·제목·반응수만 보여주고, 탭하면 상세
화면(`GET /board/post/{boardId}`)으로 가는데 그쪽이 이미 `isLike`/`isOwner` 를 내려준다.

이게 단순한 필드 정리가 아니다. **응답이 사용자에 의존하지 않게 되어서 캐시가 가능해진다**(§6).
사용자별 필드가 하나라도 남으면 캐시 키에 email 이 들어가고 히트율이 0이 된다.
이 설계에서 제일 중요한 결정이다.

`score` 도 뺀다. 마커는 `globalZIndex` 계산에 쓰지만 카드는 순서가 이미 정렬로
표현돼 있다. 내부 랭킹 값을 외부에 노출할 이유가 없다.

### 건수와 `hasMore`

- 섹션당 `20`건 (`SECTION_LIMIT`). 세로 스크롤 단일 리스트라 초안의 10건보다 늘렸다.
- `hasMore` 는 `limit + 1` 건을 뽑아서 초과분 존재 여부로 판정한다. 별도 `COUNT(*)` 를
  돌리지 않는다 — 총 개수는 UI에 안 쓰이는데 count 쿼리는 비싸다.
- 섹션별 "더보기" 페이지네이션은 **이 문서 범위 밖**이다. `hasMore` 가 true면 앱은
  화살표(`>`)만 렌더하고, 탭 동작은 다음 단계에서 붙인다.

### UI 구조 — 탭이 아니다

`sections` 는 **세로 스크롤 + 섹션 헤더** 구조다 (당근 동네지도 방식). 탭 전환이 아니다.
탭으로 만들면 첫 진입에 1개 섹션만 보여서 "아무것도 안 눌러도 뭐가 있는지 파악" 이라는
피드의 목적이 깨지고, 서버가 계산한 나머지 섹션이 낭비된다.

바텀시트 상태가 두 개라는 점은 구분한다.

| 상태 | 내용 | 제스처 |
| --- | --- | --- |
| 지도 진입 시 | **이 피드** (카드 리스트) | 세로 스크롤 |
| 마커 탭 시 | 단일 게시글 카드 | 좌우=이미지, 상하=다른 글 (루트 `CLAUDE.md` §3) |

서로 다른 화면이라 제스처 충돌은 없다.

## 5. 쿼리 설계

초안의 `radius_ids` ∪ `dong_ids` UNION CTE + 윈도우 함수 3개는 **전부 삭제**한다.
행정동 섹션이 없어져서 UNION 할 대상이 없고, 섹션이 1개라 rank 도 1개면 된다.
정렬은 `ORDER BY` 하나로 끝난다.

```sql
SELECT
    b.id,
    b.title,
    b.content,
    b.street_name,
    b.dong,
    ST_Y(b.location::geometry) AS latitude,
    ST_X(b.location::geometry) AS longitude,
    ST_Distance(b.location, ST_MakePoint(:lng, :lat)::geography) AS distance_meters,
    b.created_at,
    bm.nickname,
    bm.profile_image,
    bf.thumb_url,
    bf.file_url,
    COALESCE(agg.like_count, 0)  AS like_count,
    COALESCE(agg.reply_count, 0) AS reply_count
FROM board b
-- LEFT JOIN 유지. board_member 는 Kafka 로 복제되는 read model 이라
-- 이벤트 유실 시 행이 없을 수 있다. INNER 로 바꾸면 그 글이 조용히 사라진다.
LEFT JOIN board_member bm ON bm.email = b.email
-- 대표 이미지 1장. LEFT 라서 사진 없는 글도 남는다 (§4).
LEFT JOIN LATERAL (
    SELECT f.thumb_url, f.file_url
    FROM board_file f
    WHERE f.board_id = b.id
      AND f.file_url IS NOT NULL
    ORDER BY f.main DESC, f.id ASC
    LIMIT 1
) bf ON TRUE
LEFT JOIN LATERAL (
    SELECT
        (SELECT COUNT(*) FROM board_like  l WHERE l.board_id = b.id) AS like_count,
        (SELECT COUNT(*) FROM board_reply r WHERE r.board_id = b.id
                                              AND r.del = false)     AS reply_count
) agg ON TRUE
WHERE b.del = false
  AND b.show = 'PUBLIC'
  AND b.location IS NOT NULL
ORDER BY b.location <-> ST_MakePoint(:lng, :lat)::geography
LIMIT :limit          -- SECTION_LIMIT + 1 = 21
```

### KNN 연산자 `<->` 를 쓰는 근거

`Board.location` 은 `geography(Point, 4326)` 이다. PostGIS 2.2+ 에서 geography 타입의
`<->` 는 **인덱스 보조 정확 거리 정렬**이다 (구면 근사가 아니라 실제 최단거리 순서를 보장).
따라서 `ORDER BY location <-> pt LIMIT 21` 은 GiST 인덱스를 타고 **21건을 찾은 즉시
스캔을 멈춘다.** 전국이 대상이어도 전체 스캔이 아니다.

기대 플랜:

```
Limit
  └ Nested Loop (LATERAL)
      └ Index Scan using idx_board_location_gist on board   ← Order By: location <-> pt
```

`Nested Loop` 이 외부 정렬을 보존하고 `Limit` 이 조기 종료시킨다.
LATERAL 집계는 **21건에 대해서만** 실행된다.

주의: `LEFT JOIN LATERAL` 로 사진 없는 글도 통과시키므로 LIMIT 이 정확히 21행에서 멈춘다.
만약 나중에 `INNER JOIN` 으로 바꿔 사진 필수로 만들면, 사진 없는 글을 건너뛰느라
KNN 스캔이 21건보다 더 깊이 들어간다 (기능은 정상, 비용만 증가).

### 정렬 tie-breaker 는 Kotlin 에서 한다

같은 좌표(같은 카페 등)에 글이 여럿이면 `distance` 가 완전히 같아서 순서가 매 요청마다
뒤집힐 수 있다. 보통 `ORDER BY distance, id DESC` 로 푸는데, **SQL 에 2차 정렬 키를 넣으면
KNN 조기 종료가 깨질 수 있다** (`Incremental Sort` 노드가 끼어든다).

최대 21행이므로 **애플리케이션에서 정렬한다.** 비용이 사실상 0이고 플랜을 건드리지 않는다.

```kotlin
candidates.sortedWith(compareBy<Row> { it.distanceMeters }.thenByDescending { it.id })
```

### `r.del = false` — `COALESCE` 를 쓰면 안 된다 (해결 완료)

`board_reply.del` 이 nullable 이던 시절엔 `COALESCE(del, false) = false` 를 써야 했는데,
그러면 부분 인덱스

```sql
CREATE INDEX idx_board_reply_board ON board_reply USING btree (board_id) WHERE (del = false)
```

의 predicate 함의를 플래너가 증명할 수 없어 **인덱스를 버리고 전체 스캔**한다.
`COALESCE(del, false) = false` 는 `del IS NULL` 인 행도 통과시키는데 인덱스는 그 행을
담고 있지 않기 때문이다.

**`1fe7a37` 에서 non-null 전환이 완료**됐다 (DB `del IS NULL` 0건 확인, 엔티티
`del: Boolean = false`, `COALESCE` 제거). 이제 `r.del = false` 를 그대로 쓴다.
운영 DB 의 `NOT NULL` 제약 적용만 `docs/todo/db-index-backlog.md` 에 남아 있다.

### 왜 파생 테이블이 아니라 LATERAL 인가

기존 `MapBoardRepositoryImpl` 은 이렇게 되어 있다.

```sql
LEFT JOIN (
    SELECT board_id, COUNT(*) AS like_count
    FROM board_like
    GROUP BY board_id
) bl ON bl.board_id = b.id
```

이건 **반경 필터와 무관하게 `board_like` 전체를 스캔해서 해시 집계**한다.
`board_reply`, `board_file` 도 같은 패턴이라 매 요청마다 테이블 3개를 통째로 훑는다.
글이 1,000건일 때는 티가 안 나지만 100,000건이 되면 지도 진입이 체감으로 느려진다.

`LATERAL` 은 상관 서브쿼리라 **LIMIT 을 통과한 21행에 대해서만** 실행된다.
`board_like(board_id)` 인덱스를 21번 찾는다 — 전체 스캔보다 압도적으로 싸다.

`board_file` 도 `LATERAL ... LIMIT 1` 이라 대표 이미지 선정이 쿼리 안에서 끝난다.
지금 `MapPostService.mapPosts()` 는 파일을 배치로 다 가져와서 Kotlin 에서 O(n×m)
문자열 비교로 매칭하는데(`it.board.id.toString() == mapPostInfo.id`), 카드는 썸네일
1장만 필요하므로 그 코드가 통째로 사라진다.

### 시간 윈도우 없음

초안은 `LATEST`/`HOT` 에 7일 윈도우를 뒀다. `NEAR` 에는 **윈도우를 두지 않는다.**
지금 밀도에서 7일 필터는 피드를 비운다. 그리고 "가까운 이야기"는 오래된 좋은 글도
가치가 있다 — 신선도는 나중에 `LATEST` 섹션이 담당한다.

### 섹션 컷은 Kotlin 에서

섹션이 1개라 초안의 3섹션 중복 제거 로직(`used` 집합)은 필요 없다.
`take(SECTION_LIMIT)` + `hasMore = size > SECTION_LIMIT` 만 남는다.

섹션이 2개 이상으로 늘어나는 시점에 중복 제거를 다시 도입한다. 그때 우선순위는
**`NEAR` > `LATEST` > `HOT`** 으로 두고, 중복 판정은 **Hashids 인코딩 전 Long id** 로 한다
(문자열 비교 O(n×m) 를 반복하지 않기 위해).

## 6. 캐시 전략

### 좌표 그리드 스냅

지도 좌표는 소수점 7자리로 연속 변한다. `lat/lng` 를 그대로 키에 쓰면 히트율이 0이다.
**좌표를 격자에 스냅한다.**

```
map:feed:v2:{lat3}:{lng3}
```

- `lat3`/`lng3` = 소수점 3자리 반올림 ≈ **110m 격자**. 같은 블록 안에서 지도를
  조금씩 움직이는 동안은 같은 키를 맞는다.
- `zoom` 은 **키에서 빠졌다** — 쿼리에 영향이 없으므로(§3) 키에 넣으면 히트율만 깎는다.
  반경 캡을 도입하는 시점에 다시 넣는다.
- `siDo`/`guGun`/`dong` 도 빠졌다.
- 버전 프리픽스 — 응답 스키마가 바뀌면 올려서 통째로 무효화한다. 키에 버전을 안 넣으면
  배포 후 옛 JSON 이 역직렬화 실패로 500 을 낸다.
  **`v1` → `v2` (2026-07-29):** 응답 키를 camelCase → snake_case 로 바꿨기 때문이다.
  이게 버전 프리픽스를 둔 이유가 실제로 발생한 첫 사례다.
- **TTL 60초.** 새 글이 최대 1분 늦게 보인다. 지도 피드에서 그 정도 지연은 체감되지
  않고, 대신 지도를 흔드는 동안의 반복 요청을 전부 흡수한다.

이 캐시가 성립하는 유일한 이유는 **응답에 사용자별 필드가 없다는 것**이다(§4).

`RedisCacheManager.setAnyCacheSeconds(key, value, 60)` 를 쓴다. board 모듈의 기존 캐시가
전부 `setAnyCache`(TTL 없음)를 쓰는 게 드리프트 문제의 원인이므로 **반드시 TTL 있는
메서드**를 쓴다.

### 초안의 역지오코딩 캐시는 삭제

`geo:dong:v1:{lat3}:{lng3}` (TTL 7일)는 행정동 섹션 전용이었다. 섹션이 없어졌으므로
캐시도, Google Geocoding API 과금 걱정도 사라진다.

### 기존 카운트 캐시는 쓰지 않는다

`board_like:{boardId}` / `board_reply:{boardId}` 캐시가 이미 있지만 **TTL 이 없고 Kafka
이벤트로만 증감해서 드리프트가 누적된다.** `PostCalculateService` 는 이미 이 캐시를
신뢰하지 않고 DB 직접 집계로 우회하고 있다 (코드 주석에 이유가 적혀 있다).

피드도 **DB 집계값을 쓰고, 60초 응답 캐시로 부하를 막는다.** 드리프트 있는 캐시를 읽어서
좋아요 수가 틀리게 보이는 것보다 60초 늦은 정확한 값이 낫다.

### 캐시 스탬피드

TTL 만료 순간 동시 요청이 DB 로 몰리는 문제. 실사용자가 사실상 없는 지금은 무시한다.
DAU 가 수천을 넘으면 `SETNX` 락 또는 확률적 조기 갱신을 검토한다.

## 7. 인덱스

**신규 인덱스가 필요 없다.** 초안의 `idx_board_area_created` 는 행정동 섹션 전용이었고
그 섹션이 없어졌다. `docs/todo/db-index-backlog.md` 에서도 제거했다.

### ⚠️ 이 문서 초안의 인덱스 목록은 틀렸다 (2026-07-29 로컬 실측으로 정정)

초안은 인덱스 이름과 정의를 **실물 확인 없이** 적었다. `pg_indexes` 실측 결과 대부분이
다르다. 아래가 실제다 (`unimal_board` 스키마, 로컬).

| 실제 인덱스 | 실제 정의 | 피드에서 쓰이는 곳 | 초안이 주장한 것 |
| --- | --- | --- | --- |
| `idx_board_location` | `GIST (location)` — **predicate 없음** | KNN `<->` 정렬 | ❌ `idx_board_location_gist ... WHERE del=false AND show='PUBLIC'` |
| `idx_board_like_board_id` | `btree (board_id)` | LATERAL 좋아요 집계 | ⚠️ 이름만 다름 (`idx_board_like_board`) |
| `idx_board_reply_board_del` | `btree (board_id, del)` — 복합, 부분 아님 | LATERAL 댓글 집계 | ❌ `idx_board_reply_board ... WHERE del=false` |
| `idx_board_file_board_main_id` | `btree (board_id, main DESC, id)` | LATERAL 대표 이미지 | ❌ 초안은 "만들지 않기로 결정" 했는데 **이미 존재** |
| `idx_board_member_email` | `UNIQUE btree (email)` | `LEFT JOIN board_member` | ⚠️ `ukib2kl3...` 와 **중복 존재** |

`EXPLAIN (ANALYZE)` 실측 플랜 (`SET enable_seqscan = off`):

```
Limit (rows=21)
  └ Nested Loop Left Join (rows=21)
      └ Index Scan using idx_board_location on board b (rows=21)
            Index Cond: (location IS NOT NULL)
            Order By: (location <-> '...'::geography)      ← KNN 정상 동작
      └ Index Only Scan using idx_board_like_board_id      (loops=21)
      └ Index Scan using idx_board_reply_board_reply_created (loops=21)
      └ Index Scan using idx_board_member_email            (loops=21)
      └ Index Scan using idx_board_file_board_main_id      (loops=21)
```

확인된 것:

- `Order By: (location <-> ...)` → **KNN 순서 스캔이 맞다.** `rows=21` 로 정확히 조기 종료.
- **`Sort` / `Incremental Sort` 노드가 없다** → tie-break 를 SQL 이 아니라 Kotlin 으로 뺀
  판단이 옳았다 (§5).
- LATERAL 이 `loops=21` → 후보 21건에 대해서만 실행. 파생 테이블 전체 집계 문제가 실제로 해결됐다.

### 부분 인덱스가 아니어도 KNN 은 동작한다 (초안의 함의 논의는 무효)

초안은 "쿼리의 `del`/`show` 조건이 GiST 부분 인덱스 predicate 와 문자 그대로 일치해야
함의가 증명된다", "`show::text` 캐스팅을 맞춰야 한다" 는 주의사항을 길게 적었다.
**`idx_board_location` 에 predicate 가 없으므로 이 논의 전체가 해당되지 않는다.**
증명할 함의가 없어서 오히려 더 단순하고 안전하다.

대신 트레이드오프가 있다. 인덱스가 **비공개·삭제 글까지 담고 있으므로** KNN 스캔이 그것들을
만나면 걸러내면서 더 깊이 들어간다. 지금은 전체 29건 중 6건이 제외 대상이라 무의미한
비용이지만, 글이 수만 건이 되고 비공개 비율이 높아지면 체감된다.

**그때 부분 인덱스로 바꾸는 것이 최적화 항목**이다 (`docs/todo/db-index-backlog.md` 에 남겼다).
지금 하는 건 이르다 — 측정 가능한 문제가 없다.

### `board_reply.del` NOT NULL 전환의 근거는 틀렸었다 (결론은 유지)

커밋 `1fe7a37` 은 전환 이유를 이렇게 적었다.

> `del` 이 nullable 이면 `coalesce(del, false) = false` 를 써야 하는데, 그러면 부분 인덱스
> `idx_board_reply_board(board_id) WHERE del = false` 의 predicate 함의를 플래너가
> 증명할 수 없어 전체 스캔한다.

**그 부분 인덱스는 존재하지 않는다.** 실제는 `idx_board_reply_board_del btree (board_id, del)`
복합 인덱스이고, 복합 인덱스는 선행 컬럼 `board_id` 로 스캔한 뒤 `del` 을 인덱스 조건/필터로
쓰므로 `COALESCE` 를 써도 인덱스를 탄다. 즉 **주장된 성능 근거는 성립하지 않았다.**

그렇다고 전환을 되돌릴 이유는 없다. nullable Boolean 은 그 자체로 나쁜 모델링이고,
`COALESCE` 방어 코드가 걷혀서 코드가 단순해졌다. **결론은 맞고 근거만 틀렸다.**
(운영 DB `NOT NULL` 제약 적용은 백로그에 남아 있다.)

### 중복 인덱스 — `board_member(email)` 이 2개

`idx_board_member_email` 과 `ukib2kl3vjf09y34gk8g8i2n9d0` 이 **둘 다 `UNIQUE btree (email)`** 이다.
후자는 엔티티의 `@Column(unique = true)` 를 보고 `ddl-auto` 가 만든 것이고, 전자는 손으로
만든 것으로 보인다. 완전히 중복이라 **INSERT/UPDATE 마다 같은 일을 두 번 한다.**

피드 기능과 무관하므로 이 작업에서 건드리지 않는다. 백로그에 정리 항목으로 남겼다.

### 참고 — 피드에서 안 쓰는 인덱스

`idx_board_like_email` (실제 정의: `btree (email)` — 초안이 주장한 `(email, board_id)` 가 아니다)
는 `is_like` 판정용이다. 피드는 응답에서 `isLike` 를 뺐으므로(§4) 타지 않는다.
마커·상세 조회에서 계속 쓰이니 그대로 둔다.

### 로컬 실측이다 — 운영은 별도 확인 필요

위 목록은 **로컬 `unimal-postgis` 컨테이너** 실측이다. 초안이 "운영 DB 실물 확인(2026-07-29)"
이라고 적었는데 로컬과 이렇게 다르면 그 확인이 무엇을 본 것인지 신뢰할 수 없다.
**운영 DB 에서 같은 `pg_indexes` 쿼리를 다시 돌려 대조해야 한다.**

```sql
SELECT tablename, indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'unimal_board'
  AND tablename IN ('board','board_file','board_like','board_reply','board_member')
ORDER BY tablename, indexname;
```

이런 불일치가 생기는 근본 원인이 마이그레이션 도구 부재다 — 아래 참조.

### 곁가지: 마이그레이션 도구가 없는 게 진짜 리스크다

`ddl-auto: update` 는 컬럼 추가는 해주지만 인덱스·제약·데이터 마이그레이션은 못 한다.
`docs/todo/db-index-backlog.md` 로 손으로 추적하고 있는데 체크박스를 잊으면 무용지물이다.
**Flyway 도입을 권한다.** 1인 개발자에게 오버엔지니어링이 아니라 오히려 필수급이다 —
검토해 줄 동료가 없어서 "적용 안 된 인덱스" 를 잡아줄 사람도 없다.
이 문서 범위 밖이고 백로그에 이미 적혀 있다.

## 8. 범위 밖 (의도적으로 뺀 것)

| 항목 | 왜 뺐나 |
| --- | --- |
| `LATEST` / `HOT` 섹션 | 밀도 부족(§2). 공개 글 1,200건 넘으면 서버만 배포해서 추가 |
| 섹션별 "더보기" 페이지네이션 | 첫 진입 경험을 먼저 검증한다. `hasMore` 만 미리 내려둠. 붙일 때 **커서 기반** — offset 은 중복/누락을 만든다 |
| viewport(bbox) 기반 조회 | 지도 이동마다 재호출 + 디바운스 설계가 따라온다. KNN 방식으로 먼저 출시 |
| `PRIVATE`/비밀지도 노출 규칙 | `show = 'PUBLIC'` 만 본다. `2026-07-11-비밀지도-설계.md` 와 별도 정합성 검토 필요 |
| 광고/프로모션 카드 슬롯 | 수익화 단계에서. `sections` 배열이라 타입 추가만으로 끼워넣을 수 있다 |
| 기존 API camelCase 통일 | 앱 하위호환 이슈. 신규 API만 camelCase 로 시작 |

### 🔴 차단/신고 누적 글 필터 — 홍보 시작 전 필수

**전국이 대상이 되면서 이 항목의 위험도가 올라갔다.** 반경 기반이면 문제 글의 피해
범위가 동네였지만, 지금은 **문제 글 하나가 전국 모든 사용자의 피드 상단을 점유**할 수 있다.
글이 적을수록 더 위로 올라온다.

지금은 실사용자가 없어서 신고도 없으므로 범위 밖으로 둔다. 다만 **홍보를 시작하기 전에는
반드시 넣어야 한다.** `ReportService` 가 이미 있으므로 신고 누적 임계값으로
`WHERE NOT EXISTS (...)` 를 붙이는 정도로 시작할 수 있다.

### 참고 — `map_show` 컬럼은 존재하지 않는다

루트 `CLAUDE.md` §6 은 지도 노출 조건을
`(b.map_show = 'SAME' AND b.show = 'PUBLIC') OR b.map_show = 'PUBLIC'` 이라고 적고 있는데,
**`Board` 엔티티에 `mapShow` 필드가 없고 코드베이스 어디에서도 `map_show` 를 쓰지 않는다.**
실제 마커 쿼리는 `b.show = 'PUBLIC'` 만 본다. 피드도 같다.
`CLAUDE.md` 쪽 기술이 낡았다 — 별도로 정정이 필요하다.

## 9. 개정 (2026-07-30) — 적응형 섹션

### 무엇이 바뀌었나

섹션을 `NEAR` **하나로 고정**하던 것을, **후보 풀 크기에 따라 서버가 런타임에
섹션 수를 정하는** 구조로 바꿨다.

| | 개정 전 | 개정 후 |
| --- | --- | --- |
| 섹션 | `NEAR` 고정 1개 | 풀 < 20건 → `NEAR` 1개 / 풀 ≥ 20건 → `LATEST`·`HOT`·`NEAR` |
| 섹션당 건수 | 20 | 단일 모드 20 / 다중 모드 10 |
| 쿼리 수 | 1 | **1 (변화 없음)** |
| 캐시 키 | `map:feed:v2:` | `map:feed:v3:` |

§2 의 "공개 글 1,200건쯤 되면 `LATEST`/`HOT` 을 추가한다"는 판단 자체는 유지한다.
바뀐 건 **그 전환을 사람이 하느냐 코드가 하느냐**다. 상수에 임계값을 박아두고 매 요청
판정하면 글이 쌓이는 대로 저절로 전환되고, 그날 코드를 고치러 돌아오지 않아도 된다.

### 왜 지금 하나 — 밀도는 아직 없다

공개 글은 여전히 50건 미만이다. **이 개정으로 화면이 당장 예뻐지지는 않는다.**
지도 어디를 찍어도 풀이 20건을 못 넘으면 응답은 개정 전과 글자 하나 다르지 않다.

그래도 지금 넣는 이유는, 나중에 넣으면 **그때는 캐시 무효화·앱 검증·롤백 계획을 다시
세워야 하는 배포**가 되기 때문이다. 지금은 사용자가 없어서 잘못 나가도 비용이 0이다.
싼 시점에 구조를 넣고, 비싼 시점에는 상수만 만진다.

### 섹션별 전용 쿼리를 쓰지 않은 이유

`LATEST`/`HOT` 을 각각의 SQL 로 뽑는 게 정석이지만, KNN 후보 80건을 한 번 뽑아
메모리에서 나눈다. 공개 글이 50건 미만인 지금 **KNN 80건 = 전체 공개 글**이라
정확도 손실이 정확히 0이다. 쿼리 3개와 `(created_at)` 인덱스를 미리 만드는 건
지금 얻는 게 없는 비용이다.

**이 근사에는 유효기간이 있다.** 공개 글이 `POOL_SIZE(80)` 를 크게 넘기면
`LATEST` 가 "전국 최신"이 아니라 **"가까운 80건 중 최신"** 이 된다. 부산에 방금 올라온
글이 서울 사용자의 `LATEST` 에 안 뜬다. 공개 글 수천 건 시점에 `UNION ALL` 한 방으로
갈아탄다.

### 배정 순서와 표시 순서를 분리한다

- **배정 순서 (희소한 것 먼저):** `HOT` → `LATEST` → `NEAR`
- **표시 순서 (`FeedSectionType` 선언 순서):** `LATEST` → `HOT` → `NEAR`

`HOT` 은 반응 있는 글만 담아 후보가 가장 적다. 배정을 뒤로 미루면 앞 섹션이 그 글들을
먼저 가져가 `HOT` 이 `MIN_SECTION_SIZE(3)` 를 못 채우고 통째로 사라진다.

대가로 **방금 올라온 인기 글은 `LATEST` 가 아니라 `HOT` 에 뜬다.** 둘 다 자연스러운
자리라 감수한다.

`NEAR` 는 **sink 다.** `MIN_SECTION_SIZE` 를 적용하지 않는다 — 여기서 드롭하면 앞
섹션에 배정되지 못한 글이 피드에서 아예 증발한다.

### `has_more` 탐침은 소비 처리하지 않는다

각 섹션은 `SECTION_LIMIT + 1` 건을 집어 초과분 존재로 `has_more` 를 판정한다.
이때 **마지막 +1 건은 `used` 에 넣지 않는다.** 화면에 안 나오는 글을 소비 처리하면
뒤 섹션에서 정당하게 쓸 기회를 뺏는다.

같은 이유로, `MIN_SECTION_SIZE` 미달로 드롭되는 섹션은 **아무것도 `used` 에 넣지
않는다.** 드롭된 섹션이 글을 물고 사라지면 그 글이 뒤 섹션에도 안 나온다.

### 만지게 될 상수 (`MapFeedService.Companion`)

| 상수 | 값 | 언제 만지나 |
| --- | --- | --- |
| `MULTI_SECTION_THRESHOLD` | 20 | **화면이 초라해 보일 때 제일 먼저 손이 가는 값.** 낮추면 카드 1~2장짜리 섹션이 늘어 오히려 빈약해진다. 낮추기 전에 글부터 늘릴 것 |
| `LATEST_WINDOW_DAYS` | 7 | 밀도가 오르면 **좁힌다**(→ 2). 글이 많은데 윈도우가 넓으면 "방금 올라온 소식"에 일주일 전 글이 앉는다 |
| `SECTION_LIMIT` | 10 | 가로 캐러셀 기준. 풀폭 카드로 UI 가 바뀌면 재검토 |
| `POOL_SIZE` | 80 | 공개 글이 이 값을 크게 넘기면 위의 "유효기간" 항목대로 전용 쿼리로 전환 |

### 남은 진짜 병목

이 개정은 **API 가 준비되었다**는 뜻이지 **피드가 풍성해졌다**는 뜻이 아니다.
지금 화면이 심심한 원인은 섹션 수가 아니라 **공개 글 50건 미만**이다.
시드 콘텐츠나 초기 사용자 확보 없이는 `MULTI_SECTION_THRESHOLD` 를 아무리 낮춰도
같은 글이 섹션만 갈아입고 반복될 뿐이다.
