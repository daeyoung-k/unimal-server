# 게시글 공유 (Share)

작성일: 2026-08-07

## 1. 배경과 목표

앱에 공유 버튼이 없다. 사용자가 좋은 글을 봐도 밖으로 꺼낼 방법이 없고, 그래서
**앱 밖에서 스토맵을 마주칠 경로가 하나도 없다.** 스토어 검색이 유일한 유입이다.

동시에 스토맵의 가장 큰 약점은 cold start다. 강남 밖에서 앱을 열면 빈 지도가 나온다.
공유는 이 두 문제를 같이 건드린다 — 링크는 콘텐츠를 데리고 오기 때문이다. 누군가
"우리 동네 이 글 봐봐"라고 링크를 보내면, 받은 사람에게는 그 지역에 최소 한 개의
콘텐츠가 보장된 상태로 앱이 시작된다.

**목표는 "웹에서 글을 잘 보여주는 것"이 아니라 "앱으로 데려오는 것"이다.** 이 문장이
아래 모든 설계 판단의 기준이다.

### 비목표

- 웹에서 좋아요·댓글·로그인 — 웹을 완성품으로 만들면 앱을 깔 이유가 사라진다.
- 웹에서 지도 탐색 — 그건 앱의 핵심 경험이고, 웹으로 흉내내면 둘 다 어중간해진다.
- SEO 최적화 — 부수 효과로 따라오지만 이번 범위가 아니다.

## 2. 전체 흐름

```
[앱] 공유 버튼
      ↓  share_plus 로 URL 전달
[카톡] 링크 붙여넣기
      ↓  카카오 크롤러가 URL 을 GET
[서버] OG 태그가 박힌 HTML 응답        ← ①
      ↓
[카톡] 사진 + 제목 + 장소 미리보기 카드
      ↓  수신자가 탭
[웹] 공유 페이지                        ← ②
      ├─ 앱 있음 → 커스텀 스킴으로 앱 열기 → 게시글 상세
      └─ 앱 없음 → 스토어로
```

①과 ②가 이 스펙의 전부다.

### ①이 절반인 이유

카카오·슬랙·트위터 크롤러는 **JavaScript를 실행하지 않는다.** SPA를 띄우고 JS로
메타 태그를 채우는 방식은 크롤러 입장에서 빈 페이지다. 미리보기 카드가 안 뜨면
링크는 그냥 파란 글씨 한 줄이고, 클릭률이 자릿수로 떨어진다.

그래서 **서버가 완성된 HTML을 렌더한다.** 이 제약 하나가 아래 "렌더 위치" 결정을
사실상 정한다.

## 3. URL 설계

| 항목 | 값 |
|---|---|
| 공유 URL | `https://{share-host}/s/{hashid}` |
| 예 | `https://stomap.unimal.co.kr/s/aBc123X` |

`{hashid}` 는 기존 `HashidsUtil` 인코딩 값이다. 게시글의 Long ID 를 그대로 노출하지
않는다는 기존 정책을 그대로 따른다 — 공유 링크는 아무나 볼 수 있는 곳에 붙으므로
오히려 여기가 더 중요하다.

### 경로를 `/s/` 로 짧게 잡은 이유

카톡·문자에서 링크가 그대로 보인다. `/board/post/detail/aBc123X` 보다
`/s/aBc123X` 가 짧고, 나중에 QR·오프라인 인쇄물에 쓰기도 낫다.

### 도메인은 서버가 정한다 — 앱에 하드코딩 금지

공유 URL 을 내려주는 응답은 두 곳이다.

| API | DTO | 필드 | 비고 |
|---|---|---|---|
| `GET /board/post/{boardId}` | `PostInfo` | `shareUrl` | 공유 불가 글이면 null |
| `GET /board/map/post` | `MapPostInfo` | `share_url` | 마커는 `show='PUBLIC'` 만 오므로 항상 값 있음 |

목록 API 에는 넣지 않는다. 목록에 공유 버튼이 없고, 항목마다 URL 을 만들면 응답만
커진다.


**공유 URL 은 API 응답에 `shareUrl` 필드로 내려준다.** 앱이 `"https://..." + boardId`
로 조립하지 않는다.

이유는 하나다. **앱은 배포한 뒤에 고칠 수 없다.** 도메인을 바꾸거나 경로를 바꿀 일이
생기면, 하드코딩된 클라이언트는 스토어 심사를 다시 받아야 하고 그 사이 구버전
사용자들은 죽은 링크를 계속 공유한다. 서버가 내려주면 배포 한 번으로 끝난다.

서버 쪽 값은 설정으로 뺀다:

```yaml
custom:
  share:
    base-url: ${SHARE_BASE_URL:https://stomap.unimal.co.kr}
```

## 4. 렌더 위치 — board 모듈

api-gateway 가 아니라 **board 모듈**에서 HTML 을 렌더한다.

| 모듈 | 웹 | 게시글 데이터 | Hashids | gRPC |
|---|---|---|---|---|
| api-gateway | WebFlux | ❌ | ❌ | ❌ (의존성 자체가 없음) |
| board | Servlet MVC | ✅ | ✅ | ✅ |

게이트웨이에서 렌더하려면 `grpc-client-spring-boot-starter` 와 `proto-common` 을 새로
붙이고, 리액티브 스택에서 블로킹 gRPC 호출을 감싸야 한다. 게다가 기존
`BoardService` gRPC 는 `BoardGetResponse { string boards }` 로 JSON 문자열을 통째로
던지는 구조라 공유 페이지용으로 쓰려면 프로토콜부터 손대야 한다.

**인증·라우팅만 하던 게이트웨이가 board 도메인을 알게 되는 것**이 가장 큰 비용이다.
board 는 이미 게시글·공개범위·Hashids 를 전부 쥐고 있어 추가 의존성이 0이다.

### admin 모듈은 후보가 아니다

"board 에 HTML 이 있는 게 어색하니 admin 으로" 는 자연스러운 생각이지만, admin 은
공유 페이지와 **성격이 정반대인 모듈**이다.

| | admin | 공유 페이지 |
|---|---|---|
| 인증 기본값 | `anyRequest().authenticated()` | 비로그인이 정상 |
| 보는 데이터 | `unimal_admin` 스키마 | `unimal_board` |
| 가용성 요구 | 내가 필요할 때만 | 링크가 사는 동안 계속 |

세 가지 다 문제지만 가장 나쁜 건 첫 번째다. admin 은 "기본 잠김, 예외적으로 열림"
으로 설계돼 있어서 여기에 `permitAll` 을 뚫으면 **나중에 admin 보안을 조일 때 공유
페이지가 같이 막힌다.** 그때 원인을 찾기가 어렵다.

데이터 문제도 api-gateway 를 기각한 이유와 똑같이 반복된다 — admin 은 board 스키마를
보지 않으므로 스키마 경계를 뚫거나 gRPC 를 새로 붙여야 한다.

### 언제 `web` 모듈로 빼는가

장기적으로 옳은 답은 admin 도 board 도 아니고 **공개 웹 전담 모듈**이다. 지금 공개
페이지는 이미 두 군데로 흩어져 있다.

| 페이지 | 위치 | 성격 |
|---|---|---|
| 약관·개인정보·문의·탈퇴 | api-gateway `resources/static/` | 데이터 없음 |
| 게시글 공유 | board | 데이터 있음 |

**그럼에도 지금은 만들지 않는다.** 페이지 하나 때문에 Gradle 모듈·Dockerfile·
compose 서비스·CI 대상·모니터링 대상이 생기고, board 에 쓸 만한 gRPC 도 새로 짜야
한다(`BoardGetResponse { string boards }` 로는 못 쓴다). **1인 운영에서 프로세스가
하나 늘어나는 것이 가장 큰 비용**이고, 지금 얻는 건 깔끔함뿐이다.

대신 기준을 정해둔다. 감으로 판단하면 계속 미루거나 너무 일찍 하게 된다.

> **`web` 모듈로 분리한다: 공개 웹 페이지가 3개 이상이 되고,
> 그중 하나라도 board 밖 데이터가 필요해질 때.**

`/place/역삼동`(지역 페이지)이나 프로필 공유가 나오는 순간이 그 시점이다. 그전까지는
`service/share/` 로 격리돼 있어 옮기는 비용도 작게 유지된다.

### 게이트웨이 라우팅 — 여기서 처음으로 RewritePath 를 쓴다

board 는 `server.servlet.context-path: /board` 이므로 컨트롤러를 `/s/{hashid}` 로
매핑해도 실제 경로는 `/board/s/{hashid}` 가 된다. 공유 URL 에 `/board` 가 보이면
안 되므로 게이트웨이에서 다시 쓴다.

```
/s/{hashid}  →  rewritePath  →  /board/s/{hashid}
```

**이 저장소에서 유일한 RewritePath 다.** 다른 라우트는 전부 프리픽스를 그대로
넘기므로(`RoutePrefix` KDoc 참고), 여기만 규칙이 다르다는 걸 알고 있어야 한다.
공유 URL 의 짧음을 지키려고 감수하는 예외다.

인증 필터는 붙이지 않는다. 공유 페이지는 **비로그인 + 앱 미설치 상태에서 열리는 게
정상**이기 때문이다.

## 5. 공개 범위 정책

`Board.show` (`PostShow`) 와 `Board.del` 로 판정한다.

| 상태 | 공유 버튼 | 링크 접근 시 | HTTP |
|---|---|---|---|
| `PUBLIC` | 노출 | 정상 렌더 | 200 |
| `PRIVATE` | **숨김** | "비공개 이야기입니다" | 404 |
| `FRIENDS` | **숨김** | "비공개 이야기입니다" | 404 |
| `BLOCKED` | 숨김 | "볼 수 없는 이야기입니다" | 404 |
| `del = true` | — | "삭제된 이야기입니다" | 404 |

### 두 겹으로 막는 이유

공유 버튼을 숨기는 것만으로는 부족하다. 글이 `PUBLIC` 일 때 공유된 링크가 카톡에
남아 있고, 그 뒤에 작성자가 `PRIVATE` 로 바꿀 수 있다. **링크는 영원히 남지만 공개
설정은 바뀐다.** 그래서 렌더 시점에 매번 다시 확인한다.

### `PRIVATE` 와 `BLOCKED` 를 구분해서 보여주지 않는 이유

문구는 다르게 하되 둘 다 404 다. 200 으로 "차단된 글"이라고 알려주면 어떤 글이
차단됐는지 외부에서 열거할 수 있다.

### 없는 글도 404, 잘못된 hashid 도 404

`HashidsUtil.decode` 가 실패하는 문자열은 조용히 "없는 글"과 같게 처리한다. 디코딩
실패를 500 으로 흘리면 크롤러 요청 한 번에 에러 로그가 쌓인다.

## 6. 페이지에 담을 것

**목적은 앱 설치 유도**이므로, 흥미가 생길 만큼만 보여주고 멈춘다.

| 담는다 | 안 담는다 |
|---|---|
| 대표 이미지 1장 | 나머지 이미지 (앱에서) |
| 제목 | 댓글 목록 |
| 본문 (일정 길이에서 자름) | 좋아요 버튼 |
| 장소 (`dong` / `streetName`) | 지도 |
| 작성 시각 (상대 표기) | 작성자 이메일 |
| 작성자 닉네임 · 프로필 이미지 | 로그인 |
| 좋아요/댓글 **개수** | |
| "앱에서 보기" 버튼 | |

좋아요·댓글은 **개수만** 보여준다. 숫자는 "여기 사람이 있다"는 신호라 설치 동기가
되지만, 목록까지 보여주면 웹에서 소비가 끝나버린다.

### 공유 버튼 위치 — 지도 바텀카드가 주 진입점이다

처음에는 게시글 상세 화면(`/detail-board`) 앱바에만 뒀는데, **지도 흐름에서는 그
화면에 도달할 수 없다.** `map_bottom_card.dart` 가 `showDetailButton: false` 로
"자세히 보기" 버튼을 빼면서 바텀카드가 자기 안에서 확장(댓글·본문)을 처리하게 됐기
때문이다. 상세 화면은 게시판 탭과 푸시 알림에서만 열린다.

지도가 메인 피드인 앱에서 **공유 버튼이 게시판 탭에만 있으면 없는 것과 같다.**

그래서 네 자리에 둔다.

| 화면 | 위치 | 조건 |
|---|---|---|
| 지도 바텀카드 (사진 글) | 좋아요·댓글 오른쪽 | 중앙 카드만 |
| 지도 바텀카드 (텍스트 글) | 좋아요·댓글 오른쪽 | 중앙 카드만 |
| 지도 확장 카드 | 좋아요·댓글 오른쪽 | 항상 |
| 게시글 상세 | 앱바 우측 | 항상 |

**아이콘과 상대 위치를 넷 다 같게 맞춘다.** 글 종류나 카드 상태에 따라 버튼이
움직이면 사용자가 매번 다시 찾는다.

peek 카드(좌우로 살짝 보이는 옆 카드)에는 띄우지 않는다 — 중앙이 아닌 글을 공유하면
"내가 뭘 공유한 거지"가 된다.

### OG 태그

```html
<meta property="og:type"        content="article">
<meta property="og:title"       content="{제목 또는 본문 앞부분}">
<meta property="og:description" content="{동네} · {상대시간}">
<meta property="og:image"       content="{thumbUrl ?: fileUrl}">
<meta property="og:url"         content="{공유 URL}">
<meta property="og:site_name"   content="스토맵">
<meta name="twitter:card"       content="summary_large_image">
```

`og:image` 는 `BoardFile.thumbUrl`(400px 파생)을 우선 쓰고 없으면 `fileUrl` 로
폴백한다. 지도 피드의 `MapFeedCard.thumbnailUrl` 과 같은 규칙이다.

**제목이 없는 글이 있다** (`Board.title` 은 nullable). 이때 `og:title` 을 비우면
카톡 카드에 URL 이 그대로 노출된다. 본문 앞부분으로 대체한다.

**사진이 없는 글도 있다.** `og:image` 를 생략하면 카드가 텍스트만 남는다. 브랜드
기본 이미지로 폴백한다.

## 7. 앱으로 보내기

### 1단계: 커스텀 스킴

```
stomap://post?id={hashid}
```

현재 `AndroidManifest.xml` 과 `Info.plist` 에는 **소셜 로그인 스킴만 등록돼 있고
앱 자체의 딥링크 스킴이 없다.** `lib/screens/navigation/deep_link.dart` 에 처리
코드는 있지만 OS 가 이벤트를 만들어주지 않아 실제로는 동작한 적이 없다.

웹페이지에서 스킴을 시도하고, 일정 시간 안에 앱이 열리지 않으면 스토어로 보낸다.

### 2단계(나중): App Links / Universal Links

`https://{share-host}/s/{id}` 를 앱이 직접 받는 방식. 커스텀 스킴보다 매끄럽지만
`assetlinks.json`(Android)·`apple-app-site-association`(iOS) 을 도메인에 배포해야
하고 iOS 는 Team ID 와 엔타이틀먼트가 필요하다.

**웹페이지를 거치는 구조라 1단계만으로도 충분히 동작한다.** 2단계를 나중에 얹어도
웹페이지와 앱 라우팅 코드는 바뀌지 않는다 — 그래서 지금 안 한다.

## 8. XSS

**제목·본문·닉네임이 사용자 입력 그대로 HTML 에 들어간다.** 이스케이프를 빠뜨리면
제목에 `<script>` 를 넣은 글 하나로 공유 페이지가 뚫린다.

board 모듈에는 Thymeleaf 가 없다. 페이지가 하나뿐이라 템플릿 엔진을 새로 붙이는 건
과하므로, **문자열 조립 + 명시적 이스케이프**로 간다. 다만 이스케이프를 "잊지 않는"
방식이어야 하므로 값을 넣는 경로를 하나로 좁힌다.

`&`, `<`, `>`, `"`, `'` 를 엔티티로 치환한다. `og:*` 의 `content` 속성 안에도
동일하게 적용한다 — 속성값 탈출이 더 쉽다.

## 9. 작업 순서

1. board — `/s/{hashid}` 컨트롤러 + HTML 렌더 + 이스케이프
2. api-gateway — `/s/**` 공개 라우트 + RewritePath
3. board — 게시글 상세 응답에 `shareUrl` 추가

## 10. 나중에 볼 것

- **캐시.** 공유 링크는 크롤러가 반복해서 때린다. 지금 밀도에서는 DB 조회가 싸서
  넣지 않지만, 링크 하나가 퍼지면 같은 글을 수백 번 렌더하게 된다. Redis 에 렌더된
  HTML 을 짧게 캐시하는 게 첫 대응이다.
- **유입 측정.** 어떤 글이 공유되고 얼마나 설치로 이어지는지 모르면 개선할 수 없다.
  `?utm_source=` 수준으로 시작해도 된다.
- **공유 횟수.** 글마다 공유 수를 세면 피드 정렬 신호로 쓸 수 있다. 좋아요보다
  진심인 신호다.
