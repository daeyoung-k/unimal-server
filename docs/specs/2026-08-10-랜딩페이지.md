# 스토맵 랜딩 페이지

작성일: 2026-08-10

## 왜 필요한가

지금 외부에 내보낼 수 있는 주소가 스토어 링크뿐이다. 문제는 두 가지다.

1. **플랫폼이 반쪽이다.** 긱뉴스·디스콰이엇에 플레이스토어 링크를 걸면 iOS
   사용자가 그대로 튕긴다. 앱스토어를 걸면 반대가 된다. 폼의 URL 칸은 보통 하나다.
2. **모든 홍보가 스토어 링크에 묶인다.** 스토어 페이지는 우리가 문구·이미지·순서를
   자유롭게 못 바꾸고, 유입 측정도 안 된다.

랜딩 하나를 만들면 이후 모든 채널(스토어 등록정보의 개발자 웹사이트, 긱뉴스,
디스콰이엇, SNS 프로필, 명함)이 그 주소 하나를 재사용한다.

## 어느 모듈에 두는가 — **api-gateway**

### 결론

`api-gateway/src/main/resources/static/landing.html` + `WebPageController` 의
`GET /` 매핑. 새 모듈·새 인프라 없음.

### 근거

**이미 게이트웨이가 스토맵 웹 페이지를 서빙하고 있다.**
`WebPageController` 가 `static/` 아래 HTML을 읽어 넘기는 방식으로
`/stomap/privacy`, `/stomap/terms`, `/stomap/support`, `/stomap/delete-account`,
`/app-ads.txt` 를 이미 담당한다. 랜딩은 정확히 같은 성격의 다섯 번째 페이지다.
새 위치를 만들면 "스토맵 정적 웹 페이지"라는 하나의 책임이 두 곳으로 쪼개진다.

**푸터 링크가 상대 경로로 끝난다.**
랜딩 하단에 개인정보처리방침·약관·고객지원을 걸어야 하는데 같은 모듈이면
`/stomap/privacy` 로 끝난다. 다른 호스트에 두면 절대 URL + CORS·도메인 관리가 붙는다.

**`stomap.unimal.co.kr` 이 이미 게이트웨이를 가리킨다.**
`/s/{hashid}` 공유 링크가 이 도메인으로 들어와 게이트웨이 `ShareRouteConfig` 를
타고 board 로 간다. 즉 DNS·인증서·인그레스가 이미 서 있다. 랜딩은 같은 도메인의
루트 경로 하나를 더 쓰는 것뿐이다.

### 검토했지만 택하지 않은 안

| 안 | 왜 아닌가 |
| --- | --- |
| **board 모듈** | board 가 HTML을 렌더하는 건 사실이지만(`SharePageService`) 그건 *게시글* 을 렌더하는 도메인 기능이다. 서비스 소개는 게시글 도메인과 무관하다. 여기 두면 board 가 "게시글 + 회사 홈페이지" 두 책임을 갖는다. |
| **S3 + CloudFront 정적 호스팅** | 구조적으로는 이게 제일 깔끔하다(서버 부하 0, 배포=업로드). 하지만 `stomap.unimal.co.kr` 을 게이트웨이와 나눠 쓰려면 CloudFront behavior 분기 + 인증서 + 배포 파이프라인이 새로 생긴다. 랜딩 트래픽은 무시할 수준이라 **얻는 게 없는 복잡도**다. 1인 운영에서 배포 경로를 하나 늘리는 비용이 더 크다. |
| **별도 프론트엔드 프로젝트 (Next.js 등)** | 페이지 한 장에 빌드 파이프라인·의존성·배포를 새로 만드는 건 명백한 과잉이다. |
| **Vercel / Cloudflare Pages** | 무료이고 빠르지만 도메인·배포처가 하나 더 늘고, 푸터 링크가 크로스 도메인이 된다. |

### 나중에 옮겨야 할 신호

- 랜딩에 블로그·업데이트 노트처럼 **페이지가 늘어나기 시작**할 때
- 문구 하나 고치려고 게이트웨이를 재배포하는 게 실제로 거슬릴 때
- 랜딩 트래픽이 게이트웨이 지표를 오염시킬 때

그때 S3 + CloudFront 로 빼면 된다. HTML이 정적 단일 파일이라 이전 비용이 거의 없다 —
지금 게이트웨이에 두는 결정이 나중을 막지 않는다.

## 경로 설계

| 경로 | 내용 | 비고 |
| --- | --- | --- |
| `GET /` | 랜딩 | 신규 |
| `GET /s/{hashid}` | 게시글 공유 페이지 | 기존, board 로 rewrite |
| `GET /stomap/privacy` | 개인정보 처리방침 | 기존 |
| `GET /stomap/terms` | 이용약관 | 기존 |
| `GET /stomap/support` | 고객 지원 | 기존 |
| `GET /stomap/delete-account` | 계정 삭제 안내 | 기존 |
| `GET /app-ads.txt` | AdMob 판매자 인증 | 기존, 루트 필수 |

**루트로 둔 이유**: 이 주소는 사람이 외워서 치고 스토어 등록정보에도 박힌다.
`/stomap/landing` 처럼 만들면 그 이점이 사라진다. 게이트웨이 라우트는 전부
프리픽스 기반이라 루트와 충돌하지 않는다.

**`api.unimal.co.kr/` 도 같은 랜딩이 뜬다.** 같은 게이트웨이이므로 그렇다.
Host 헤더로 분기할 수 있지만, API 도메인 루트에 소개 페이지가 뜨는 게 해가 없어
분기하지 않는다.

## nginx — 화이트리스트에 경로를 열어야 한다

게이트웨이에 `GET /` 를 추가한 것만으로는 `stomap.unimal.co.kr/` 이 열리지 않는다.
`docker/nginx/nginx.conf` 의 `stomap.unimal.co.kr` 서버 블록은 **경로 화이트리스트**로
되어 있고, 맨 아래 `location / { return 404; }` 가 나머지를 전부 막는다.
(API 전체가 두 이름으로 노출되는 걸 막기 위한 의도된 설계다.)

그래서 다음 4개를 열었다.

| location | 용도 |
| --- | --- |
| `= /` | 랜딩. **정확 매칭**이라 API 는 그대로 닫혀 있다 |
| `/img/` | OG 커버·아이콘·스크린샷 |
| `= /favicon.ico` | 랜딩이 참조 |
| `= /app-ads.txt` | AdMob 판매자 인증 |

**`location /` (프리픽스)로 열면 안 된다.** 그러면 `/user/auth/...`, `/board/...` 가
이 호스트로도 닿아서 화이트리스트 설계가 무너진다. 루트만 필요하므로 `= /` 를 쓴다.

검증 (nginx 매칭 우선순위 기준):

```
/                    → = /              200
/img/stomap-og.png   → /img/            200
/app-ads.txt         → = /app-ads.txt   200
/s/aBc123            → /s/              200
/user/auth/login     → /                404  ← API 는 여전히 닫힘
/board/post/list     → /                404  ← API 는 여전히 닫힘
```

`nginx_local.conf` 는 `server_name localhost` + `location /` 전체 프록시라 수정
불필요하다.

### app-ads.txt 가 왜 여기 필요한가

`app-ads.txt` 는 원래 `api.unimal.co.kr/app-ads.txt` 로만 열려 있었다. 스토어
등록정보의 "개발자 웹사이트"가 `api.unimal.co.kr` 였기 때문이다.

랜딩이 생기면 개발자 웹사이트를 `stomap.unimal.co.kr` 로 바꾸게 되는데, 그 순간
구글은 **바뀐 도메인의 루트**에서 `app-ads.txt` 를 찾는다. 여기를 안 열면
AdMob 판매자 인증이 조용히 깨진다(광고가 즉시 멈추지는 않지만 인증 상태가 풀린다).
개발자 웹사이트 변경과 이 location 은 한 세트다.

## OS 분기 — 서버 리다이렉트를 쓰지 않는다

버튼 링크만 클라이언트 JS로 바꾼다. 서버에서 302로 스토어로 던지지 않는다.

이유는 **크롤러**다. 카카오·슬랙·구글이 루트를 먼저 긁는데 리다이렉트로 던지면
미리보기 카드가 통째로 죽는다. 공유 페이지에서 인증 필터를 뺀 것과 같은 이유다
(`ShareRouteConfig` KDoc).

데스크톱은 어느 스토어로 보내도 반은 틀리므로 분기하지 않고 하단 텍스트 링크
두 개를 쓰게 둔다. iPadOS 13+ 는 UA를 `Macintosh` 로 위장하므로
`navigator.maxTouchPoints` 로 함께 판별한다.

## 이미지 자산

**CDN(`cdn.unimal.co.kr`)을 쓰지 않고 게이트웨이 `static/img/` 에 함께 둔다.**

`cdn.unimal.co.kr` 은 사용자 업로드 사진용 S3 버킷 + CloudFront 다. 여기에 사이트
자산을 섞으면 성격이 다른 두 종류가 한 버킷에 들어가고, 문구 하나 바꿀 때
업로드 + 캐시 무효화가 별도 절차로 붙는다. 전부 합쳐 **668KB** 라서 jar 에 넣어도
부담이 없고, HTML과 이미지가 같은 커밋으로 움직이는 이점이 더 크다.

| 파일 | 출처 | 규격 | 용량 |
| --- | --- | --- | --- |
| `static/img/stomap-og.png` | `share-default.png` 재사용 | 1200×630 | 74KB |
| `static/img/stomap-icon.png` | `stomap-icon-512.png` 축소 | 256×256 | 12KB |
| `static/img/shot-1~7-*.webp` | 스토어 iOS 스크린샷 축소 | 720×1564 | 합 530KB |

### 변환 기준

- **스크린샷: 1320×2868 → 폭 720 webp(q82).** 랜딩 표시폭이 240px 이므로 3배.
  PNG 로 두면 3.7MB, webp 로 530KB — 7배 차이라 webp 로 간다. Safari 14+ 부터
  지원하므로 폴백은 두지 않는다.
- **OG 이미지는 webp 로 바꾸지 않는다.** 카카오 등 일부 크롤러가 webp 를
  렌더하지 못해 미리보기 카드가 빈다.
- 모든 `<img>` 에 `width`/`height` 를 박아 로딩 중 레이아웃 점프를 막는다.

### OG 커버를 새로 만들지 않은 이유

공유 페이지 기본 이미지(`share-default.png`)가 이미 1200×630 이고
"지도 위에 남기는 나의 스토리" 카피 + 로고가 들어가 있다. 랜딩 OG 로 그대로 맞다.
새로 만들면 같은 브랜드 자산이 두 벌이 된다.

## 스크린샷 품질 이슈 (랜딩 전에 판단 필요)

현재 스토어 스크린샷을 그대로 재사용했다. 랜딩에 걸어보면 드러나는 문제가 있다.

1. **같은 고양이 사진이 3장(2·3·6번)에 반복 등장한다.** 캐러셀을 넘기는 사람에게는
   "올라온 글이 이것뿐인가"로 읽힌다. 서로 다른 스토리가 담긴 컷으로 2장은 교체하는
   게 좋다.
2. **텍스트 마커 말풍선이 펼쳐진 컷이 없다.** 다른 앱에 없는 시각 요소인데
   2·3번에 빈 말풍선 아이콘만 작게 보인다. 줌 16.8 이상에서 제목이 들어간 말풍선
   카드가 뜬 화면을 새로 찍으면 캐러셀에서 가장 눈에 걸리는 컷이 된다.
3. **내 지도(5번)·내 스토리 목록(7번)에 사진 없는 텍스트 글이 대부분이다.**
   회색 문서 아이콘이 줄줄이 보여 앱이 비어 보인다. 사진 글이 섞인 계정으로
   다시 찍는 게 낫다.
4. **1번 컷에서 마커 라벨이 겹친다.** `+2` 스택 배지와 "미세랑 나들이" 캡션이
   붙어 읽히는데, 대표 컷이라 이건 앱 버그로 보일 수 있다. 실제 UI 문제인지
   확인이 필요하다.

지금 상태로 올려도 동작에는 문제가 없다 — 다만 위 4개는 랜딩의 첫인상을
직접 깎는다.
