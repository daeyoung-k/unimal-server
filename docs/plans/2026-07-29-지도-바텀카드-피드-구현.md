## 단계 1 — 요청/응답 DTO

| 파일 | 내용 |
| --- | --- |
| `board/.../controller/map/dto/MapFeedRequest.kt` | `latitude: Double`, `longitude: Double`, `zoom: Int?` |
| `board/.../service/post/dto/map/MapFeedResponse.kt` | `sections: List<MapFeedSection>` |
| `board/.../service/post/dto/map/MapFeedSection.kt` | `type: FeedSectionType`, `title: String`, `hasMore: Boolean`, `items: List<MapFeedCard>` |
| `board/.../service/post/dto/map/MapFeedCard.kt` | 스펙 §4 필드. 프로퍼티는 camelCase + 클래스에 `@JsonNaming(SnakeCaseStrategy)` |
| `board/.../service/post/enums/FeedSectionType.kt` | `NEAR` 만. `title: String` 프로퍼티 |

`MapFeedRequest` 에 `@field:NotNull` 로 위경도 필수 검증. `zoom` 은 nullable 이고
**쿼리에 넘기지 않는다** — 스펙 §3 참조. DTO에 주석으로 "현재 미사용, 반경 캡 도입 대비"를
남겨서 나중에 죽은 파라미터로 오해받지 않게 한다.

`FeedSectionType` 은 지금 값이 하나뿐이라 enum 이 과해 보이지만, 섹션 추가가
예정된 확장 지점이므로 처음부터 enum 으로 둔다.

```kotlin
enum class FeedSectionType(val title: String) {
    NEAR("지금 여기 이야기"),
}
```

초안의 `titleTemplate` + `{dong}` 치환은 삭제한다 (행정동을 모른다).

`MapFeedCard` 주의사항:

- `boardId` 는 **Hashids 인코딩된 문자열**. raw PK 를 노출하지 않는다.
  쿼리는 Long id 를 반환하므로 조립 단계에서 인코딩한다.
- `HashidsUtil` 은 object 가 아니라 **주입받는 빈**이다 (`private val hashidsUtil: HashidsUtil`) —
  `PostService` 와 동일하게 생성자 주입.
- `thumbnailUrl`, `imageUrl` 은 **nullable** (사진 없는 글 포함, 스펙 §4).
- `distanceMeters` 는 `Int` 로 내린다 (미터 단위 소수점은 의미 없다). 쿼리는 `double precision`
  을 주므로 조립 시 `.toInt()`.
- `title` 은 `board.title` 이 nullable 이라 `String?`.

## 단계 2 — 후보 조회 리포지토리

**파일:** `board/.../domain/board/map/MapFeedRepositoryImpl.kt` (신규)

기존 `MapBoardRepositoryImpl` 을 고치지 않고 새 클래스를 만든다. 마커 쿼리는 앱이 이미
쓰고 있어서 회귀 위험을 지고 싶지 않다. LATERAL 개선은 피드에서 먼저 검증하고,
안정되면 마커 쿼리에 이식한다 (후속 작업).

- [ ] `@Repository` + `@PersistenceContext EntityManager` (기존 스타일 동일)
- [ ] 스펙 §5 의 KNN 쿼리를 native query 로 작성
- [ ] 반환 타입은 내부 전용 `MapFeedCandidate` data class

### 파라미터 반복 사용

`ST_MakePoint(:lng, :lat)::geography` 가 `SELECT`(거리 계산)와 `ORDER BY`(KNN) 두 곳에
나온다. Hibernate native query 는 **같은 named parameter 반복 사용을 지원**하므로
`setParameter("lat", ...)` 한 번으로 충분하다.

### 결과 매핑을 row index 로 하지 말 것

기존 `MapBoardRepositoryImpl` 은 `row[0]`, `row[13]` 같은 인덱스 접근이다.
컬럼을 중간에 하나 추가하면 그 아래 전부 밀려서 **컴파일은 통과하고 런타임에 깨진다.**
찾기 제일 어려운 종류의 버그다.

`Tuple` 을 쓴다. `EntityManager` 를 유지하면서 제일 싼 방법:

```kotlin
em.createNativeQuery(sql, Tuple::class.java)
    .setParameter("lat", lat)
    .setParameter("lng", lng)
    .setParameter("limit", limit)
    .resultList
    .map { it as Tuple }
    .map { t ->
        MapFeedCandidate(
            id             = (t.get("id") as Number).toLong(),
            title          = t.get("title") as String?,
            thumbUrl       = t.get("thumb_url") as String?,
            fileUrl        = t.get("file_url") as String?,
            distanceMeters = (t.get("distance_meters") as Number).toDouble(),
            likeCount      = (t.get("like_count") as Number).toLong(),
            createdAt      = (t.get("created_at") as Timestamp).toLocalDateTime(),
            // ...
        )
    }
```

컬럼명 기반이라 순서가 바뀌어도 안전하고, 이름이 틀리면 즉시 예외가 난다.

- [ ] 모든 nullable 컬럼(`title`, `street_name`, `dong`, `thumb_url`, `file_url`,
      `nickname`, `profile_image`)을 `as String?` 로 받는지 확인

## 단계 3 — 서비스 조립

**파일:** `board/.../service/post/MapFeedService.kt` (신규)

`MapPostService` 에 넣지 않는다. 마커 조회와 피드 조립은 책임이 다르고,
`MapPostService` 는 이미 파일 매칭 로직으로 비대하다.

흐름 (초안의 6단계 → 5단계, 역지오코딩 단계가 사라짐):

1. **응답 캐시 조회** — `map:feed:v2:{lat3}:{lng3}`, 히트면 즉시 반환
2. **후보 조회** — 단계 2 리포지토리, `limit = SECTION_LIMIT + 1`
3. **정렬 tie-break + 섹션 컷**
   - `sortedWith(compareBy { distanceMeters }.thenByDescending { id })` (스펙 §5)
   - `hasMore = candidates.size > SECTION_LIMIT`
   - `items = candidates.take(SECTION_LIMIT)`
   - `items` 가 비어 있으면 `sections = emptyList()` (스펙 §2)
4. **Hashids 인코딩 + DTO 변환** — `thumbnailUrl = thumbUrl ?: fileUrl`
5. **응답 캐시 저장** — `setAnyCacheSeconds(key, response, 60)`

### 상수는 companion object 에

```kotlin
companion object {
    private const val SECTION_LIMIT = 20
    private const val FEED_CACHE_TTL_SECONDS = 60L
    private const val GRID_SCALE = 3          // 좌표 소수점 반올림 자리수 ≈ 110m
}
```

숫자를 코드에 흩뿌리면 나중에 튜닝할 때 어디를 바꿔야 하는지 찾게 된다.
이 값들은 데이터가 쌓이면 **반드시 조정하게 될** 값이다.

초안의 `MIN_SECTION_SIZE` 는 사실상 1이 되어 상수로 둘 의미가 없다 —
"비어 있지 않으면 포함" 이라 조건문으로 표현한다.
`FRESH_WINDOW_DAYS` 는 시간 윈도우가 없어져서 삭제.

### 캐시 유틸 — TTL 있는 메서드를 쓴다

`RedisCacheManager.setAnyCacheSeconds()` 가 이미 정의돼 있는데 board 모듈에서 호출하는
곳이 하나도 없다. 기존 캐시가 전부 `setAnyCache`(TTL 없음)를 쓰는 게 드리프트 문제의
원인이다. 피드는 **반드시 TTL 있는 메서드**를 쓴다.

- [ ] `setAnyCacheSeconds` 로 저장하고 실제 TTL 이 붙는지 `redis-cli TTL <key>` 로 확인
      (`-1` 이 나오면 TTL 없는 메서드를 쓴 것)

### 좌표 격자 스냅

```kotlin
private fun snap(v: Double): String = "%.3f".format(v)
```

`String.format` 은 로케일에 따라 소수점이 `,` 가 될 수 있다. 캐시 키가 환경마다 달라지면
디버깅이 지옥이다.

- [ ] `String.format(Locale.ROOT, "%.3f", v)` 로 로케일 고정

### 쿼리 플랜 (가장 중요)

`EXPLAIN (ANALYZE, BUFFERS)` 로 아래를 확인한다. 하나라도 어긋나면 쿼리가 아니라
**인덱스 predicate 함의가 깨진 것**이므로 스펙 §7 을 다시 본다.

**인덱스 이름은 실측값이다** (스펙 §7). 초안에 적혀 있던 이름들(`idx_board_location_gist`,
`idx_board_reply_board` 등)은 **실제로 존재하지 않는다** — 그 이름으로 찾으면 헛수고한다.

- [x] `board` → `Index Scan using idx_board_location` **+ `Order By: location <-> ...`**
      (`Order By:` 줄이 없으면 KNN 이 아니라 그냥 필터로 쓰인 것 → 전체 정렬 발생)
- [x] 최상단이 `Limit` 이고 그 아래가 `Nested Loop` 인지 (조기 종료 확인)
- [x] `Sort` / `Incremental Sort` 노드가 **없는지** (있으면 KNN 조기 종료가 깨짐)
- [x] `board_like` → `Index Only Scan using idx_board_like_board_id`
- [x] `board_reply` → `Index Scan using idx_board_reply_board_reply_created`
- [x] `board_file` → `Index Scan using idx_board_file_board_main_id`
- [x] `board_member` → `Index Scan using idx_board_member_email`
- [x] LATERAL 이 `loops=21` 인지 (후보에만 실행되는지 — 파생 테이블 문제 해결 확인)
- [x] `rows` 실측이 21 인지 (전국 글 수만큼 나오면 LIMIT 이 안 밀린 것)

**2026-07-29 로컬 실측 결과 — 전부 통과.** `SET enable_seqscan = off` 기준
`Execution Time: 81.636 ms` (대부분 PostGIS 함수 초기화 오버헤드).

> 주의: 로컬 글 수가 극소수(공개+좌표 보유 **23건**)라 기본 플랜은 플래너가 **일부러
> Seq Scan 을 고른다** — 47 버퍼 스캔이 인덱스 하강보다 싸기 때문이다. 정상이다.
> 그래서 `SET enable_seqscan = off` 로 "인덱스를 탈 수 있는 쿼리인지"만 확인했다.
> 진짜 성능 검증은 데이터가 쌓인 뒤 기본 플랜으로 다시 한다.
