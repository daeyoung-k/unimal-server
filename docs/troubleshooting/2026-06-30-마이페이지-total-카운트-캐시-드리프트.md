# 마이페이지 "내 스토리"/받은 좋아요 total 카운트 캐시 드리프트

> 작성일: 2026-06-30
> 관련 파일: `board/service/post/PostCalculateService.kt`, `PostManager.kt`, `LikeManager.kt`,
> `kafka/topics/PostKafkaTopic.kt`, `kafka/consumers/post/PostConsumer.kt`,
> `domain/board/BoardRepository.kt`, `domain/board/like/BoardLikeRepository.kt`,
> `utils/RedisCacheManager.kt`

## 증상

마이페이지 "내 스토리" 세그먼트에 표시되는 글 수(total)와 실제 글 리스트 개수(13개)가 맞지 않음.

## 데이터 흐름 — 세 숫자의 출처가 다름

| 화면 요소 | 엔드포인트 | 집계 |
| --- | --- | --- |
| 세그먼트 "내 스토리 N" | `GET /board/post/total` → `getPostTotalCount` | **Redis 캐시** `user:{email}:postCount` |
| 하단 리스트 | `GET /board/post/my/list` → `boardMyConditionList` | DB 조회, **size=20 페이지네이션** |
| 지도 마커 | (Flutter `_located`) | 리스트 중 위치 있는 글만 |

리스트와 total은 **같은 기준**(`del=false` 전체 글)을 써야 하지만, 한쪽은 DB 직접 조회, 한쪽은 Redis 캐시라 값이 갈렸다.

## 카운팅 메커니즘 — Redis 값이 바뀌는 시점

`user:{email}:postCount`는 **딱 두 경우에만** 증감한다 (`PostService` → `PostKafkaTopic` → `board.postCountCalculateTopic` → `PostConsumer` → `PostCalculateService.postCountCalculate`):

| 시점 | 코드 | 이벤트 | 동작 |
| --- | --- | --- | --- |
| 글 작성 | `posting()` (L82) | `INCREMENT` | 현재값 +1 |
| 글 삭제 | `postDelete()` (L334) | `DECREMENT` | 현재값 -1 (0 이하 방지) |

- 글 **수정**은 개수 변화 없음 → 이벤트 없음(정상).
- 조회 시 `getPostTotalCount`는 Redis를 먼저 보고, **값이 없을 때만**(`null`) DB `count(del=false)`로 1회 계산해 캐시를 채운다.

## 카운팅 대상 = 전체 게시글 (사진/텍스트 무관)

- `posting()`: `boardRepository.save()`로 글 저장 → 사진 업로드(`if files`)는 **별개 분기**, 카운트 `INCREMENT`는 그 바깥에서 **무조건** 발행. 즉 사진 0장 텍스트 글도 +1.
- `postDelete()`: `del=true`(soft delete) + `DECREMENT` 무조건(본인 글).
- DB 재계산 쿼리 `getUserTotalPostCount`: `count(b) where email and b.del != true` → 삭제 안 된 **전체** 글.

## 근본 원인 — 캐시 드리프트

1. **Redis에 TTL이 없음.** `PostManager.saveUserTotalPostCount` → `RedisCacheManager.setAnyCache`는 `set(key, value)`로 **만료 없는 영구 저장**. 한 번 어긋나면 자동 복구가 안 됨.
2. **카프카 발행이 실패를 삼킴.** `PostKafkaTopic.postCountCalculateEvent`는 발행 실패 시 `logger.error`만 찍고 예외를 던지지 않음 → 글 저장 트랜잭션은 커밋됐는데 카운트 이벤트만 유실되는 순간(브로커 일시 장애, 컨슈머 실패, 과거 데이터 마이그레이션, 직접 DB 조작 등)이 생기면 차이가 영구히 남음.

리스트가 13개면 size=20 미만이라 안 잘린 것 → **실제 글 = 13개가 맞고, Redis 캐시값이 틀어진 것.**

## 수정 (2026-06-30, 적용함)

`PostCalculateService`에서 total 조회를 **Redis 캐시 경유 → DB 직접 집계**로 변경. 캐시 드리프트 원천 제거.

```kotlin
fun getLikeTotalCount(email: String): Long =
    boardLikeRepository.getUserTotalLikeCount(email)

fun getPostTotalCount(email: String): Long =
    boardRepository.getUserTotalPostCount(email)
```

- 카운트 기준은 **전체 글(del=false) 유지** — 의미 변화 없음, 항상 정확.
- 받은 좋아요 수(`getLikeTotalCount`)도 동일하게 DB 직행. (좋아요한 글 수 `getLikedStoriesCount`는 원래부터 DB 직행이라 무관)
- 게시글/좋아요 count는 인덱스로 가볍고 마이페이지 진입 시에만 호출 → 캐시 제거해도 비용 부담 없음.

## 후속 작업 (미적용 — 의도적으로 남김)

이번엔 **"일단 남김"**으로 결정. 카운트용 카프카/Redis 파이프라인이 죽은 채로 계속 동작한다:

- 글 작성/삭제·좋아요마다 `postCountCalculateEvent`/`likeCountCalculateEvent` 발행 → consumer가 `getXxxTotalCount`(이제 DB count) 호출 후 Redis write. **아무도 안 읽는 값에 매번 DB 쿼리 + 쓰기**가 발생.
- 추후 정리 시 들어낼 대상:
  - 발행: `PostService.posting`/`postDelete`/좋아요 토글의 `postKafkaTopic.*CountCalculateEvent(...)`
  - `PostKafkaTopic.postCountCalculateEvent` / `likeCountCalculateEvent`
  - `PostConsumer`의 두 `@KafkaListener`
  - `PostCalculateService.postCountCalculate` / `likeCountCalculate`
  - `PostManager`/`LikeManager`의 Redis 카운트 메서드(`getUser*Count`, `saveUser*Count`)
  - 카프카 토픽 설정(`board.postCountCalculateTopic`, `board.likeCountCalculateTopic`) 정리
- 기존에 어긋나 있던 Redis 키(`user:*:postCount`, like 카운트)는 이제 안 읽히니 방치 무해. 거슬리면 삭제:
  ```bash
  redis-cli --scan --pattern 'user:*:postCount' | xargs -r redis-cli del
  ```
